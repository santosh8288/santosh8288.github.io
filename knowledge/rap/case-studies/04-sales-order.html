Sales Order — Action & Status Control

A sales order is useful for explaining explicit business actions such as Submit, Confirm and Cancel rather than treating every business operation as a generic update.

Case studiesAll scenarios01 · Purchase Order Approval02 · Travel Management — Draft to Active03 · Supplier Invoice — Validation & Determination04 · Sales Order — Action & Status Control05 · Employee Onboarding — Authorization & Feature Control06 · Plant Maintenance Request — EML07 · Stock Transfer — Transaction & Validation08 · Customer Credit Review — Approval & Authorization09 · Project Expense Claim — Draft + Validation + Approval
The important design lesson is that an action should represent a meaningful business command. For example, Confirm Order can enforce status rules and authorization before changing the order state.

Behavior

managed implementation in class zbp_i_salesorder unique;
strict ( 2 );

define behavior for ZI_SalesOrder alias SalesOrder
persistent table zsales_order
lock master
{
  create;
  update;
  delete;

  action submit result [1] $self;
  action confirm result [1] $self;
  action cancel parameter ZD_CancelReason result [1] $self;

  validation validateOrder on save { create; update; }
}

Action state machine

DRAFT │ Submit ▼ SUBMITTED │ Confirm ▼ CONFIRMED │ Cancel ▼ CANCELLED Each action checks the current state before changing it.

Architectural rule

Do not expose an unrestricted Status update merely because the database field exists. If status transitions are business operations, expose actions and enforce the allowed transition matrix in the backend.

Production note: The code is intentionally a teaching/reference skeleton. CDS entity names, database fields, message classes, authorization implementation, released APIs and syntax can vary by ABAP platform/SAP S/4HANA release.
