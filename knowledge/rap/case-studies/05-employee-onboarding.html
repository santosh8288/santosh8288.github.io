Employee Onboarding — Authorization & Feature Control

An employee onboarding request demonstrates the difference between authorization and feature control: who may operate on the object versus whether an operation is currently available because of the object's state.

For example, HR users may be allowed to approve onboarding requests, while the Approve action is only enabled when the request is in Submitted state. RAP authorization is role/user based; feature control can depend on instance state. SAP documents this distinction explicitly. citeturn0search16

Behavior

managed implementation in class zbp_i_onboarding unique;
strict ( 2 );

define behavior for ZI_Onboarding alias Onboarding
persistent table zonboarding
lock master
authorization master ( instance )
{
  create;
  update;
  delete;

  action approve result [1] $self
    features : instance;

  action reject parameter ZD_Rejection result [1] $self
    features : instance;
}

Feature-control idea

If Status = 'SUBMITTED' → Approve enabled → Reject enabled If Status = 'APPROVED' → Approve disabled → Reject disabled If Status = 'REJECTED' → Submit may be enabled The exact feature-control implementation depends on the authorization and release model used by the target system.

Authorization idea

Use RAP authorization control so backend access is restricted by user role/authorization objects. Do not depend on hiding a button in the UI for security. citeturn0search16
